# Evidence-driven branch strategy: frozen development result

DEV_REPAIR_BRANCH_STRATEGY1 demonstrates actual branch continuation, but no
additional repaired bugs. Both arms repaired Mockito-17 and Jsoup-54 twice and
failed Mockito-23 twice: 4/6 each. No policy is promoted.

## Intervention and protocol

Under Anthony Mets's direction, Codex authored a generic playbook asking the
agent to inspect declarations, explicitly choose a graded parent or reset,
read virtual source before extension, distinguish exception movement from proof
and inspect existing configuration mechanisms instead of chasing each failing
class. No bug-specific patch or fixed revision was supplied. This is externally
authored strategy development, not a self-learned improvement.

The prospective protocol froze at `f8a4bf0e`, after 102 focused tests passed.
Both arms have application feedback, multi-file submissions and branches.
Only the child playbook changes. Model, case evidence, four-round allocation,
eight-request ceiling, token ceiling and compiler/test gates are equal.
Three exposed Java bugs, two repetitions, alternating order, USD 0.20 total
API ceiling. Historical trials were preserved without edits. No reserved cases
or fixed revisions were consumed.

All 38 calls have cost receipts: **USD 0.051932875**. No inapplicable
submission occurred. The child used branches in both Mockito-23 repetitions,
with maximum depth two. Verification checks digests, pairing, budgets, arm-specific
genome identities and earlier graded parents; it is not independent replication.
Time excludes baseline preparation; API cost excludes infrastructure.

The reference stopped after a charged truncated answer in repetition one
(4096 completion tokens) and an explicitly empty submission in repetition two.
The child completed four validated attempts in each repetition. Different
realised request counts are therefore not different authorised budgets, but
the cost comparison includes early stops and cannot isolate branch-token savings.
There was no observed 404 or execution interruption.

## Diagnostic evidence

In child repetition one, exceptions progressed through `ReturnsDeepStubs$1`,
`DelegatingMethod` and `MockUtil`, then remained at `MockUtil` after reset.
The third attempt investigated serializable child-mock settings. This is a
plausible causal direction, not a verified repair. The partial branch never
passed the trigger test.

In child repetition two, exceptions remained `ReturnsDeepStubs$2` after the
first extension, then became `ReturnsDeepStubs$1` after reset and remained there.
The second hypothesis suspected a different object despite the unchanged
exception. Several rationales described metadata as nonserializable, although
the buggy `GenericMetadataSupport` declaration already implements Serializable.
These are signs of insufficient grounding; preserving edits alone does not
correct a mistaken causal model. Changed exceptions are not counted as success.

The next development hypothesis is a concise structured record of the observed
failure, relevant source citation, predicted test transition and contradiction
check before selecting an extension. This has not yet been implemented or
measured. The priority is evidence quality, not maximising branch count.

All production trees were verified restored. Canonical memory remains 292 events.
Success patches, failed proposals, lineage and costs are preserved in artifacts;
this retention is not claimed as newly learned canonical skill. No general RSI
or transfer beyond these exposed cases is demonstrated.
