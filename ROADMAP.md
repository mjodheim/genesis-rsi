# Genesis roadmap

**Direction reset: 6 October 2026**

The historical L/M/A experiment ladders remain preserved evidence. They are no longer the reader-facing roadmap for the active architecture.

The new roadmap measures progress from software self-extension toward efficient recursive machinery improvement.

## Historical integrity note

## North-star objective

Build a persistent software lineage that can:

1. observe its own limitations;
2. identify which part of its machinery caused them;
3. invent or acquire a more capable or more efficient mechanism;
4. test descendants under prospective matched budgets;
5. preserve only validated improvements;
6. use retained improvements to make later improvements easier;
7. repeat the cycle with decreasing external assistance.

Genesis is explicitly not a programme for scaling a monolithic Transformer.

## G1 — Language substrate

**Development status (2026-10-06): FOUNDATION IMPLEMENTED.** The common six-family substrate is working; Python uses CPython AST while the other initial families currently use conservative structural parsing. Compiler-grade semantic adapters remain pending.

**Goal:** understand unfamiliar software structurally without embedding bug-specific human recipes.

Deliverables:
- common language-adapter protocol;
- syntax-tree representation;
- symbols/types/references where toolchains expose them;
- normalized compiler/linter/test evidence;
- adapters for Python, Java, C#, Rust, Go and TypeScript/JavaScript;
- versioned documentation retrieval interface;
- tests proving adapters expose facts rather than repair answers.

Exit evidence:
- the same language-neutral operation can be materialized in at least three language families;
- no external LLM is required for parsing, validation or operation execution.

## G2 — Universal operator IR

**Development status (2026-10-06): FOUNDATION IMPLEMENTED.** A Python-derived subscript-index operator transfers to Java, TypeScript and C# with zero model calls in the development demo. A frozen external causal campaign remains pending.

**Goal:** retained transformations become portable concepts.

Deliverables:
- canonical operator schema;
- structural and semantic preconditions;
- content-addressed identity and provenance;
- language-specific materializers;
- replay and ablation.

Exit evidence:
- an operator learned from one language causally solves fresh tasks in another language family;
- literal patch memorization fails an appropriate control.

## G3 — Failure model

**Development status (2026-10-06): FOUNDATION IMPLEMENTED.** Evidence-backed attribution now distinguishes knowledge, representation, operator, search, retrieval, toolchain, planner, evaluation, unknown and underdetermined classes. Prospective attribution validation remains pending.

**Goal:** distinguish could-not-solve from why-the-machinery-could-not-solve.

Deliverables:
- taxonomy of failure causes;
- evidence-backed attribution;
- confidence/ambiguity recording;
- explicit unknown/underdetermined outcome;
- retained capability-gap events.

Current implementation:
- `genesis/learning/failure_model.py`
- `genesis/learning/capability_gaps.py`
- `genesis/learning/self_extension.py`

Exit evidence: prospective failures are separated into representation, operator, search, retrieval, toolchain and budget classes often enough to improve later intervention choice.

## G4 — Self model

**Development status (2026-10-06): FOUNDATION IMPLEMENTED.** Genesis can build a content-addressed map of mutable machinery and trust-root boundaries, preserve component ambiguity, and map attributed failures to intervention candidates. Static-control validation remains pending.

**Goal:** Genesis has a causal, machine-readable model of its own active architecture.

Deliverables:
- component graph and versioned identities;
- inputs/outputs and resource accounting;
- known failure modes;
- mutable vs trust-root boundaries;
- intervention points.

Exit evidence: Genesis selects a limiting internal component from observed evidence and outperforms static always-change-X controls.

## G5 — Autonomous experiment generation

**Scientific status (2026-10-07): PROJECT-DEFINED GATE PASSED.** A prospectively preregistered five-arm experiment was generated by Genesis from a fresh operator failure before holdout reveal. On the sealed six-case C# holdout, the unchanged parent and structural-operator arms solved 0/6, while the universal_operator_ir arms solved 5/6 with zero external model calls; ablating the winning component reduced performance to 0/6. See docs/G5_QUALIFICATION_2026-10-07.md.

The result is bounded, project-created and external-to-lineage rather than independent third-party validation. It does not establish G6 or general RSI.

**Goal:** Genesis designs experiments about its own hypotheses.

Deliverables:
- hypothesis records;
- intervention generation;
- matched controls;
- prospective holdouts;
- budget plans;
- automatic evidence collection.

Exit evidence: at least one useful internal improvement is discovered through an experiment whose hypothesis and candidate interventions were generated by Genesis rather than directly authored for the result.

## G6 — Component evolution

**Scientific status (2026-10-07): PROJECT-DEFINED GATE PASSED.** Genesis diagnosed an over-specific internal matcher from prior G5 evidence, generated three source-level descendants of `universal_operator_ir`, selected the smallest variant that retained 9/9 prior/safety behaviors, froze it before a fresh eight-case C# holdout reveal, and improved from 2/8 parent to 8/8 descendant under the same candidate budget with zero external model calls. Reverting the selected machinery mutation reduced performance back to 2/8. See `docs/G6_QUALIFICATION_2026-10-07.md`.

The result is bounded and project-created; it does not establish G7, independent third-party validation or general RSI.

**Goal:** mutable machinery can produce materially different descendants.

Candidate mutable families: retrieval, memory policy, planner, scheduler, operator generation, representation, routing, specialist mechanisms and mutation/search policy.

Exit evidence: fresh matched-budget evaluation shows a lineage-produced descendant dominates or extends its parent on the capability/resource frontier.

## G7 — Causal promotion and rollback

**Goal:** automate safe lineage descent without letting mutable Genesis own the verdict.

Deliverables: candidate isolation, evaluator identity, fresh-case identity, ablation, promotion records, rollback and tamper detection.

Much of the lower-level transition apparatus already exists in the cognitive-machinery line and should be reused rather than rebuilt.

Exit evidence: repeated candidate generations can be accepted/rejected automatically under a prospectively frozen authority while exact rollback and evidence replay remain available.

## G8 — Distillation and local specialization

**Goal:** convert repeated expensive reasoning into cheaper retained machinery.

Priority order:
1. deterministic operator/program;
2. compact index/table;
3. small specialist statistical model;
4. larger learned component only when previous forms are insufficient.

Exit evidence:
- external-model calls per solved fresh task decrease while useful performance is retained or improves;
- at least one expensive behavior is replaced by a materially cheaper local mechanism.

## G9 — Successor generation

**Goal:** Genesis N produces a better Genesis N+1.

Minimum criterion:
- material machinery change;
- lineage-produced proposal;
- prospective fresh evaluation;
- matched resource accounting;
- causal ablation;
- retained capability;
- no evaluator ownership by mutable lineage.

A single transition is evidence of self-improvement, not yet recursive self-improvement.

## G10 — Recursive successor chain

**Goal:** demonstrate repeated causal improvement.

Target evidence: `G0 -> G1 -> G2 -> G3` where each child improves on fresh evidence, inherits earlier useful capabilities, uses inherited machinery to contribute to the next improvement, and remains within explicit resource limits.

This is the first point at which Genesis should seriously claim domain-bounded RSI.

## Beyond G10 — toward more general RSI

A general-RSI research programme would broaden the same mechanism beyond software repair and internal software architecture to learning algorithms, representations, scientific reasoning, experiment design, specialist model training, architecture search and resource allocation across heterogeneous cognitive mechanisms.

No date or claim is attached to this horizon. It requires evidence that the software-domain successor loop actually works first.

## Resource strategy

The project does not begin by purchasing frontier-scale compute.

Resource order:
1. improve algorithms and representations;
2. improve search efficiency;
3. retain reusable abstractions;
4. distill repeated reasoning;
5. parallelize independent experiments;
6. add local accelerator capacity only when measurement shows it is the binding constraint.

Compute should be purchased because an empirically valuable loop is compute-bound, not because AI requires GPUs.
